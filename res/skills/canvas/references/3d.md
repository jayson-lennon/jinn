# Real 3D with three.js

The vendored 3D library: math surfaces, vector fields, molecules, model
viewers, gamedev/computer-graphics scenes. This file carries the loading
pattern (three.js is an ES module, unlike every other vendored library),
the genre recipes, and the honesty rules about when 3D is the wrong
answer.

**Scope note:** three.js is for scenes that need a camera, lighting, or
perspective. Toy 3D (a spinning cube, a bouncing ball with no lighting
model) and 2D animation stay in p5; 2D physics stays in matter.js.
That routing lives in `interactive-and-simulation.md`.

## Loading — import map, then module script

three.js ships ES modules only; there is no script-tag build. Two blocks
in `<head>`, in this order:

```html
<script type="importmap">
{
  "imports": { "three": "/vendor/three/three.module.min.js" },
  "scopes": { "/vendor/three/": { "three": "/vendor/three/three.module.min.js" } }
}
</script>
<script type="module">
  import * as THREE from 'three';
  import { OrbitControls } from '/vendor/three/addons/controls/OrbitControls.js';
  // ... scene code ...
</script>
```

- The **import map must precede the module script**. Addons are separate
  files under `/vendor/three/addons/` that import the bare `three`
  specifier — the `scopes` entry resolves that specifier to the vendored
  core so addon files never fail.
- The map goes in the template as a **commented block**; uncomment both
  it and a module script. A page with the map but no module script is
  harmless (the map only declares what `three` resolves to).
- Mixing with the UMD libraries is fine: KaTeX and Chart.js globals are
  visible to module scripts; module `import`s are visible to later
  classic scripts only if explicitly hung on `window`.
- There is no live-reload trap here: a syntax error in the module script
  kills that script only — the rest of the page and the reload wiring
  stay alive. Check the browser console, not just the page.

## The minimal lit scene (memorize this shape)

Every 3D artifact is a variation on: renderer, scene, camera, lights,
geometry+material, render loop. With OrbitControls for the "rotate and
inspect" expectation:

```js
const renderer = new THREE.WebGLRenderer({ antialias: true });
renderer.setPixelRatio(Math.min(devicePixelRatio, 2));
renderer.setSize(container.clientWidth, container.clientHeight);
container.appendChild(renderer.domElement);

const scene = new THREE.Scene();
scene.background = new THREE.Color(getComputedStyle(document.body)
  .getPropertyValue('--bg')?.trim() || '#111');

const camera = new THREE.PerspectiveCamera(50, w / h, 0.1, 100);
camera.position.set(3, 2.5, 4);

scene.add(new THREE.AmbientLight(0xffffff, 0.4));
const key = new THREE.DirectionalLight(0xffffff, 1.2);
key.position.set(4, 6, 3);
scene.add(key);

const controls = new OrbitControls(camera, renderer.domElement);
controls.enableDamping = true;

function animate() {
  controls.update();          // required when damping is on
  renderer.render(scene, camera);
  requestAnimationFrame(animate);
}
animate();

// Keep the canvas honest across window resizes:
new ResizeObserver(() => {
  camera.aspect = container.clientWidth / container.clientHeight;
  camera.updateProjectionMatrix();
  renderer.setSize(container.clientWidth, container.clientHeight);
}).observe(container);
```

- **Standard materials need lights.** A `MeshStandardMaterial` with no
  light in the scene renders black; the forgotten light is the "my 3D
  is invisible" bug. (Unlit alternatives: `MeshBasicMaterial`, which
  needs no lights — right for flat data marks.)
- `controls.update()` in the loop is required when `enableDamping` is
  set, or the camera dead-stops.
- `setPixelRatio` + the resize observer are what keep the scene crisp
  instead of blurry or letterboxed.
- Color management (r152+): colors specified in sRGB, renderer converts
  internally; don't fight it — set colors with `new THREE.Color('#4a9')`
  and move on.

## Genre recipes

### Surface z = f(x, y) — multivariable calculus, loss surfaces

Code geometry, no assets: sample the function onto a plane geometry and
displace vertices. Color by height, add axes, allow orbiting:

```js
const f = (x, y) => Math.sin(x) * Math.cos(y);
const geo = new THREE.PlaneGeometry(6, 6, 120, 120);
const pos = geo.attributes.position;
for (let i = 0; i < pos.count; i++) {
  const x = pos.getX(i), y = pos.getY(i);
  pos.setZ(i, f(x, y));
}
geo.computeVertexNormals();

const mesh = new THREE.Mesh(geo, new THREE.MeshStandardMaterial({
  color: 0x4a9edd, side: THREE.DoubleSide, roughness: 0.6,
}));
scene.add(mesh);
```

- `computeVertexNormals()` after displacement — without it the surface
  shades flat and the shape reads wrong.
- Contour lines on the surface: a second material pass with a
  fragment-shader stripe, or simpler, a `LineSegments` grid laid at
  z-levels — only when contours carry the point.
- For **gradient descent / loss landscapes**, drop a small sphere at the
  start point and animate it stepping downhill (`f`'s numeric gradient);
  sliders for learning rate. This is the single most-requested ML
  visual, and it's ~40 lines.
- Annotate like a 2D plot: axes as `Line` + `Sprite` labels (canvas
  texture per label), min/max markers. A naked surface is a texture;
  labeled features are the lesson.

### Vector fields, gradient fields, flows

Arrows from a 3D grid of sample points; `ArrowHelper` for small counts,
one merged `LineSegments` for thousands (one geometry, one draw call —
per-arrow objects die past a few hundred). Color arrows by magnitude.
For flows on the field, animate particles stepping along the field;
`Points` with a per-frame position update is cheap and readable.

### Embeddings / multivariable data in 3D scatter

`THREE.Points` + `BufferGeometry` with a color attribute — hundreds of
thousands of points, one draw call. UMAP/t-SNE output is exactly this.
**But run the 3D-honesty check first** (bottom of this file): most 3D
scatters answer worse than a well-encoded 2D one, because depth is
unreadable without orbiting and occlusion hides clusters. Reach for 3D
when the third dimension carries real information the user will
actually inspect by rotating — not for decoration.

### Molecules / crystal lattices — ball-and-stick

Hard-coded atomic coordinates in, spheres + cylinders out. No chemistry
library needed:

```js
const atoms = [
  { el: 'C', pos: [0, 0, 0],      r: 0.77, color: 0x333333 },
  { el: 'H', pos: [1.09, 0, 0],   r: 0.37, color: 0xdddddd },
  { el: 'H', pos: [-0.36, 1.03, 0], r: 0.37, color: 0xdddddd },
];
const bonds = [[0, 1], [0, 2]];
for (const a of atoms) {
  const m = new THREE.Mesh(new THREE.SphereGeometry(a.r, 24, 16),
    new THREE.MeshStandardMaterial({ color: a.color }));
  m.position.set(...a.pos);
  scene.add(m);
}
for (const [i, j] of bonds) {
  const a = new THREE.Vector3(...atoms[i].pos), b = new THREE.Vector3(...atoms[j].pos);
  const mid = a.clone().add(b).multiplyScalar(0.5);
  const cyl = new THREE.Mesh(
    new THREE.CylinderGeometry(0.08, 0.08, a.distanceTo(b), 12),
    new THREE.MeshStandardMaterial({ color: 0x888888 }));
  cyl.position.copy(mid);
  cyl.quaternion.setFromUnitVectors(new THREE.Vector3(0, 1, 0),
    b.clone().sub(a).normalize());
  scene.add(cyl);
}
```

- Coordinate data comes from the model (VSEPR geometry, crystal unit
  cell) — the agent writes the numbers, three.js draws them. This is
  the honest 3D answer for simple molecules; the 2D structural-formula
  gap in `specialist-and-scientific.md` is unchanged for anything
  ring-fused or aromatic, where hand-built 3D coordinates would assert
  geometry we didn't compute.
- Same recipe draws crystal lattices (repeat the cell with a loop) and
  orbital models (sphere + `TorusGeometry` rings).

### Model viewers — STL / OBJ / glTF

For "open this model file" asks: copy the model next to the artifact as
a sibling file and load it with the matching addon
(`STLLoader`, `OBJLoader`, `GLTFLoader` — all at
`/vendor/three/addons/loaders/`). Center and frame the loaded geometry
before first render; add the same three-light + OrbitControls treatment
as every scene. STL is the common ask (3D printing); note that STL has
no units — pick and label a scale. Loading from disk means the artifact
no longer travels alone; say so if the user moves the file.

### Gamedev / computer-graphics concept demos

One concept per scene, labeled: **perspective camera** (draw the
frustum as `CameraHelper`), **PBR vs Phong** (same sphere, two
materials side by side, one light), **shadow maps** (a ground plane +
`castShadow`/`receiveShadow` + the light's `shadow.camera` bounds),
**terrain from a noise function** (the surface recipe with a different
`f`), **character controller** (`PointerLockControls` addon) or
**orbit-vs-first-person camera** comparison. These scenes teach by
being poked — pair each with OrbitControls and a one-line caption
stating the concept; that caption is what makes it an explanation
rather than a screensaver.

### Orbiting camera or turntable, always

Every scene gets either OrbitControls (user-driven) or a slow auto
turntable (`controls.autoRotate = true` needs `controls.update()` in
the loop too). A fixed-camera 3D scene is the artifact equivalent of a
photo of a sculpture — the one view the author liked, not the object.

## Antipatterns

- **3D everything.** When the user says "make it 3D", ask what the
  third dimension *encodes*. "Depth for realism" is not information;
  the 2D artifact with better encoding usually wins. (This file exists
  so that the honest-3D cases have a real answer — not so every ask
  gets one.)
- **Unrotatable 3D.** A scene without OrbitControls or auto-rotation
  asserts one view of a 3D object; if one view is honest, the artifact
  was 2D. Ship the controls.
- **The black scene.** Standard material, no lights — renders as a
  silhouette at best. Lights are part of the scene, not styling.
- **Per-point/per-arrow `Mesh` objects.** Thousands of scene-graph
  nodes stall the tab; merge into one `BufferGeometry` (`Points`,
  `LineSegments`) and color with attributes. Merging is the difference
  between 60fps and a frozen page.
- **Label-less 3D.** No axes, no unit note, no feature annotations —
  the reader can't tell a 10× loss surface from a 0.01× one. 3D plots
  need *more* annotation than 2D, not less.
- **Import map after the module script.** The browser applies the map
  to module scripts that follow it; a map placed after (or in another
  file loaded later) leaves `three` unresolved and the whole module
  silently never runs.
- **Commenting out the map but keeping a module import.** If the page
  imports `three`, it needs the map, full stop. When in doubt, the
  template's commented block ships both pieces together.
- **glTF with external textures referenced by path** — fine only if the
  texture files ship as siblings; a glTF whose textures live at
  upstream URLs violates the offline rule. Inline or copy assets.
- **Physics via three.js.** three.js renders; it does not simulate.
  Rigid-body asks route to matter.js (2D — say plainly that 3D physics
  is not vendored) or hand-rolled kinematics for simple orbits and
  projectiles, which don't need an engine anyway.
