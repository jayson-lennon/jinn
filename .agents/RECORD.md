# The Record

A curated list of factual, scoped statements asserting the application's **current** state. Authoritative for the present, never the future.

The planner consults this file before proposing a plan. If a feature **contradicts** an entry here, the contradiction is surfaced before the plan proceeds. If a feature **establishes a new high-level fact**, a verbatim entry is proposed for human approval as part of the plan.

## Why This File Exists

A planner reads this file _instead of_ reading the code, so an entry earns its place only by being **expensive to re-derive** — a decision, a boundary, a user-visible behavior, or a fact whose only copy is scattered across several files.

If a reader could recover the fact from one grep or one file read, it does not belong here. Most things do not belong here. The list is expected to be short, and adding an entry is a claim that the fact is not already obvious from the code.

Deleting an entry is always safe; a planner that needs it will find it. A record that grows to mirror the codebase costs every future planner and goes stale within weeks.

## Format Rules

- **Factual.** Assert how things are _now_. Never future intent ("we will...", "should..."). Each entry is the current state of the application.
- **Durable.** Every entry must survive a routine change. Apply the **rename test**: if the codebase renamed this thing tomorrow — a config key, a crate, a type, an actor, an event, a schema version — would the entry be false? If yes, it is not a fact about the application; it is a fact about today's source tree. Delete it.
- **Scoped.** Name what each entry applies to — repo, app, frontend, or a named subsystem. An unscoped fact (e.g. "uses Fossil") is ambiguous: is that the repo, or the app's supported VCS list? Always disambiguate.
- **High-level.** One-liners (a few sentences at most). Capture decisions and facts a planner needs, not implementation minutiae.
- **Single tag.** Each entry carries exactly one subsystem tag as a `(tag)` prefix: `- (tools) The bash tool runs...`. One entry, one tag — this keeps tag usage a meaningful coverage metric (a tag growing large signals over-specification or a tag that should split). If you cannot decide between two tags for an entry, that is a signal to **re-evaluate the entry itself**, not to assign both. Use `(tag)` rather than `[tag]` to avoid colliding with markdown task-list (checkbox) syntax.
- **Tag subsystem scope.** It's not always obvious what tag to use for a given record entry. Pick based on existing tags or somewhat related subsystem. As particular tags start to become numerous, evaluate whether a new tag (subsystem) should be created based on the content of the tags. It's normal for subsystems to form after-the-fact so feel free to propose re-tagging of existing records.
- **Singular concept.** Each entry should be a single sentence and only concerned with a single concept. Prefer multiple entries versus combining many things into one.

## Templates

| Pattern     | Form                                                             | Example                                                                                             |
| ----------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| State       | `[Scope] currently [does X / is Y].`                             | "(TUI) The TUI's first screen at startup is the chat screen."                                       |
| Persistence | `[Scope] persists [what] to [where].`                            | "(sessions) Sessions persist to SQLite."                                                            |
| Flow        | `[Input/event] is handled by [actor/subsystem], which [action].` | "(tools) File edits route through the `edit` tool, which requires a unique match or `replace_all`." |
| Boundary    | `[Scope] is bounded by [constraint].`                            | "(projects) Project discovery walks ancestors until a VCS root or `$HOME`, whichever comes first."  |

## Absence

A missing record, or an un-recorded area, simply means the list has no entry there yet. Absence is not a constraint — it is an open question, and a feature that fills a gap may establish the first entry for that area (proposed for human approval as part of the plan).

- (ui) The selected option in an attendant properties choice row uses a dedicated attendant-option theme key, distinct from the focus accent.
- (attendant) An attendant is an ordinary session for storage: it is created with the persist flag set, so it is saved on creation and on every turn, exactly like a subagent's child; `is_persistable` checks the flag before any other clause, so a false there would be terminal for the session's life.
- (attendant) SqliteSessionStore::save returns Ok for a non-persistable snapshot, so a swallowed save is indistinguishable from success — proof that a session reached a store must assert on store contents, never on the return value.
- (attendant) The manual re-run (R) and the trigger fire are separate run preparations, not one function with a mode flag: R always seeds through the template and cascades a cancel, while a trigger respects the mode and cancels only the attendant's own turn.
- (attendant) An attendant in prep mode is marked paused in the sidebar and cannot be run; the ⏸ marker means prep mode and nothing else.
- (attendant) An attendant whose trigger is parent-completed is marked in the sidebar with ⇉.
- (attendant) The properties panel cages the cursor on the two rows above the prep row while prep mode is on, because a row that governs nothing is one the cursor has no business resting on; the rows below it are never caged, since an attendant being composed still has a tool and skill budget.
- (attendant) The properties panel's popup height is derived from the field list, so adding a row cannot leave the height disagreeing with the rows the view draws.
- (attendant) A manual re-run must drive its own session phase to Idle before dispatching, because the enqueue handler queues any user message arriving while a session is Sending or Streaming.
- (attendant) A manual re-run cancels via cancel_streaming rather than cancel_stream_and_drain, because the drain would steer the aborted partial into the input box.
- (attendant) A reset-mode run writes its forced-exclusions to the store; without that, a restarted attendant would silently regain its full history.
- (attendant) The seed template's prior-report placeholder is replaced with a first-run sentence when no report exists, so no run ever dispatches a raw template token.
- (attendant) The attendants sidebar section is scoped to the active session's parent context, so a parent shows its own attendants and an attendant shows its siblings.
- (attendant) Field movement in the properties popup clamps at both ends rather than wrapping, so the cursor never silently teleports to the opposite edge.
- (attendant) Attendant run configuration is three facts: a trigger (manual or parent-completed), a behavior (reset or preserve), and prep mode. A newly created attendant is in prep mode.
- (attendant) The default seed template describes the situation rather than prescribing a kind of work, so it reads sensibly for an attendant that is not inspecting code; existing attendants keep their stored template, since the default only fills an absent key.
- (attendant) The properties popup's default field focus is the first one, so every field stays reachable under clamping navigation.
- (attendant) The parent-completed trigger fires every attendant in the subtree under the completed session, not just its direct children: an attendant created under another attendant is still under the parent the user asked.
- (kernel) Every bus message is published through its own spawned task, so a Vec of messages is not an ordered sequence; two messages that depend on each other (push then pin) must be one message, because the second silently no-ops when it arrives first.
- (sidebar) The sidebar's section order is stated in three places — the nav chain, the layout's registration table, and the live registration — and a test pins all three to the same order, since nothing stops them drifting apart otherwise.
- (attendant) The parent-completed trigger never cancels a running attendant: a busy attendant's in-flight turn is real work, so the trigger's seeded turn queues behind it. Cancelling there aborted a turn the user was waiting on and left a "Cancelled" entry behind.
- (session) Publishing a `CancelStream` message stops the inference actor but does not move the session's own phase; the phase transition is a separate local call. Anything that needs the session to accept a new turn immediately must make both.
- (session) A message enqueued while a session is Sending/Streaming waits in its queue, and a later cancel drains that queue into the input box as editable draft text — so a message that was meant to run can surface as a draft the user never sent.
- (attendant) Every attendant seed prompt ends with the parent session's id, appended after the user's own template text. An attendant runs in its own session and cannot otherwise reach the transcript it reports on, so a session-search tool has nothing to search by without it.
- (attendant) A seed prompt whose attendant has no parent on record ends with "The parent session's id is unavailable", so the line reads as a finished sentence rather than trailing off after "is".
- (attendant) An attendant's behavior governs context only: reset force-excludes every non-pinned entry so the run sees pins alone, preserve appends to the conversation as it stands. A behavior never decides whether a run happens.
- (attendant) A parent-completed trigger fires in preserve mode. Suppressing the dispatch there, on the theory that an unattended run should not inject a message, left such an attendant permanently inert with nothing on screen saying why — the template is the user's own statement of the attendant's purpose.
- (tools) session_fetch prints each line as `#N (entry-id) role: text`. The bracketed position it used to print looked pasteable but is a display label that shifts as a session grows, so passing one as `entry_id` resolved to some other entry — often in a different session. A bare integer `entry_id` is now rejected with an error naming the confusion.
- (tools) The `report` and `notify_parent` tools are offered only to attendant sessions; every other session's tool list omits them, the same per-session filter server tools get per provider. A non-attendant has no conclusions to report and no parent to wake, so a visible tool there is one that can only fail.
- (attendant) The tool an attendant calls to record its result is `conclude`, not `report`. A run concludes once, so the terminal name stops an agent calling it repeatedly to build a wall of text; only the most recent entry seeds the next run, so extra calls are dropped anyway. The log it writes to is still a report.
- (tools) A tool's declared parameter list must match the arguments its executor actually reads. A schema naming a property the executor ignores accepts a valid-looking call and then rejects it for a missing argument, which reads to the agent as a broken tool.
- (tools) "May this session use this tool" has three gates — the session's tool filter, the provider gate for server tools, and the attendant gate for the attendant-only family — and one predicate decides all three. The prompt assembler and the tool dispatcher both call it; deciding the gates at separate call sites is what let the picker list tools the prompt hid.
- (tools) A tool withheld from a session's prompt is refused at dispatch, by its own rejection rather than the unknown-tool one: the tool exists and is registered, so "unknown" would be false and would send the model hunting for a spelling instead of telling it the tool is out of scope. A session absent from state withholds nothing — defaulting to withheld there refuses every tool for a session the actor has not seen.
- (tools) A session's tool filter is a mode plus glob patterns and supports an allow list as well as a deny list; a deny list is the former blocklist. An allow list is absolute, so it withholds MCP tools it does not name — the case a blocklist cannot express, since there is no entry to remove. The mode governs an empty name list as strictly as a populated one.
- (tools) An allow list is absolute including when empty: it withholds every name it does not name, and an allow list naming nothing withholds every name.
- (tools) A tool filter entry is a glob over the tool's namespaced name, so `mcp__<server>__*` covers a whole MCP server without enumerating its tools, and a bare tool name is matched exactly.
- (tools) The attendant-only tool filter is a subtraction, never a substitution: an attendant keeps every ordinary tool and gains its own two. Filtering _to_ the attendant tools leaves one that cannot read, search or edit.
- (attendant) An attendant in prep mode is the only kind marked with a pause glyph beside its title; the predicate lives on the session, so no renderer re-derives it.
- (attendant) A saved attendant persists its instructions as a role and a text only; entry ids, timestamps, token counts, and pin positions are derived at creation or deliberately left out. A persisted token count is the one that was actively wrong: `fill_missing_token_counts` skips any entry that already carries one, so a saved count was never recomputed and stayed stale forever.
- (attendant) A saved instruction's role is required, not defaulted: a user instruction and an agent result with identical text are different messages to the model, and nothing in the text tells them apart. Defaulting a missing role to `user` would restore an attendant's own prior turns as facts it was told.
- (attendant) A saved attendant carries only user and assistant instructions, the kinds `entries_to_messages` turns into a message. A tool result is a snapshot of a file as it was, so re-injecting it into a newly spawned attendant asserts stale contents as current fact.
- (attendant) A saved attendant's `pins` renders inline as one `key = value` on its entry, alongside `model`, so an attendant is a single readable block rather than a block trailed by sub-tables that read as further attendants.
- (config) An attendant restored from a saved entry pins each instruction as relative, and the session store owns a pin's position from then on. Re-saving returns every pin to relative, which is the cost of not storing the position; a relative pin is what survives a reset run, because reset force-excludes everything unpinned.
- (config) A multi-segment list key's leaf is the segment after the last dot and its parent path is everything before. Naming those two halves backwards sent the resolver walking to the leaf, and because the resolver creates the tables it passes through, every save grew a stray table named after the leaf at the document root.
- (config) A value nested inside a list entry renders inline as `key = value`, never as a sub-table or sub-list. A nested `[[entry.sub]]` header is a _sibling_ of its entry in TOML's grammar, not a child: it reads as the next entry, and whether it binds to the right one came down to field sort order.
- (config) Whether a nested value renders as a table is declared, not inferred from its shape. The patcher is handed a list of _sections_; an unregistered table is by definition a value and renders inline. Inferring from "is it all tables?" made the same value render two different ways depending on which save path reached it.
- (config) A value's rendered form must not depend on whether its key already existed in the document. When it did, one path rewrote it inline and another rewrote it as a header, so re-saving an unchanged attendant moved the user's own file. The byte-identical-save invariant held only for entries with no nested values, because an empty array already rendered inline and never reached the disagreement.
- (config) The top-level entry list stays a header-form array-of-tables. That form is what lets the patcher match entries by key and rewrite one without disturbing its siblings; only values _inside_ an entry render inline.
- (attendant) Attendant sessions render in hot pink (RGB 255, 105, 180), distinct from the purple that marks subagent sessions. The previous dusty rose passed the theme's minimum distance gate by a hair (d² 2772 of 1500) yet still read as the same color; hot pink sits at d² 11922.
- (session) The chat pane's indicator row names the active session's kind when it is a subagent or an attendant, as a right-aligned bracketed label in that kind's color, shown in every phase including idle. The chat pane has no title bar, so the session list's colors — the only other signal — are off-screen exactly when the user is reading; an idle session is the case that most needed naming and the one the row's "not busy, draw nothing" early return had been silently suppressing.
- (session) The session preview popup's border carries the previewed session's kind color — attendant pink or subagent purple — and the ordinary unfocused border color for every other kind. The popup answers what a session _is_ before it is opened, and for these two kinds that is the one question its title cannot carry. Origin is the discriminator throughout, so a fork of an attendant conversation is an ordinary session again and reads as one.
- (ui) The attendants sidebar section binds the same activation keys as the sessions section, so an attendant's conversation can be opened from either list. Opening one previously required routing through the sessions list, even though the attendants section already had the highlighted session in hand.
- (session) A session's kind label survives beside the busy indicator rather than replacing it, because the spinner cannot remain a widget: a widget takes the whole area it is handed and there is no way to hold a second element at its right edge. The throbber becomes a `Line` via `to_line`, which reads the same `ThrobberState` — and still needs normalizing before the read, or the stored step drifts out of range across an idle stretch and the widget has to clamp it back.
- (session) Advancing the busy indicator's animation step is gated on a spinner actually being drawn. Once a kind label alone can get the row past the early return, an idle attendant session draws every frame, and an ungated step would spend that idle time spinning up a spinner it never shows.
- (sidebar) Removing a session leaves the sessions cursor on the row it occupied, clamped to the new last row.
- (sidebar) The attendants cursor returns to the attendant it was on when that attendant is removed, clamped to the new last one.
- (watchdog) The stall watchdog's restart budget counts consecutive silent stalls between completed provider generations, so a stream that emits tokens before dying still escalates. Activity resets the silence clock but not the count: a retry that connects and then dies again is the same fault recurring, not a recovery. The budget is restored by a completed generation — `Finished` or a `ToolUse` boundary — or by surrender; an exhausted budget belongs to the turn that gave up, not to the next one the user starts. It deliberately survives the dispatch that a stall retry issues, since that re-arm is the same code path as any dispatch and clearing there would restart every retry at attempt 1.
- (watchdog) A stall retry excludes the partial entries from context rather than removing them, so a discarded attempt stays visible in the chat log where the user watched it appear. Removal made the stall invisible exactly when it mattered most; exclusion gives the same valid prompt without deleting evidence. Exclusion alone was not sufficient — the chat log collapses any contiguous run of `!is_in_context()` entries at or past the collapse threshold and further than the proximity window from the tail, and it cannot tell a discarded stall from a block the user chose to ignore, so the attempt was registered as an expanded ignored block as well. The retry also rewinds `Streaming` back to `Sending`, since staying in `Streaming` made the retried dispatch's first token an illegal transition.
- (session) A tool result is created in whichever busy phase the session is in, so a tool call and its result stay adjacent in history. Results arrive in `Sending` — the stream ended in `ToolUse` before the batch ran — so gating on `Streaming` dropped every one of them and left the finalized result pushed detached at the end of history.
- (rules) Stream rules live in `jinn.toml` as `[[stream_rules.entry]]`, each pairing regex `conditions` and stream `scopes` with the markdown `body` injected when the rule fires. They are the only rule kind that runs mid-response: `[[tools.bash_command_policy]]` blocks a command before it runs and `[[context_curation.auto_prune.regex.rules]]` prunes completed history, so neither can catch a model doing something it was told not to do while it is still doing it.
- (rules) A stream rule is tested against the accumulated buffer of one stream only — assistant prose, reasoning, or a single tool call's serialized arguments are buffered separately — so a rule scoped to tool arguments cannot fire on prose that merely mentions the same text. A `tool:<name>(<glob>)` scope filters which calls the rule applies to and never what the condition reads: an admitted call hands the whole argument buffer to the regex, content included. Path-like values for the glob are scanned out of that buffer rather than parsed, because tool arguments arrive as partial JSON that is frequently unparseable — and scanning is what lets such a rule fire from the first delta that names the file.
- (rules) A stream rule's matching happens before the offending delta is published, so no token of an intercepted output reaches the chat log. The intercept then ends the response with a reason distinct from a user cancel, because the two abort for opposite reasons and every consumer must be able to tell them apart.
- (rules) A stream-rule intercept sends the inference actor its own abort command rather than a cancel. A stream task cannot abort itself, so it returns a verdict and the actor performs the teardown — and reusing the cancel path would have the actor emit a second, cancelling completion that races the intercept's own, pushing a `Cancelled` entry into an interrupted turn's history. The abort carries the generation it stopped, because the resume arms a new dispatch before the bus delivers it and an unstamped abort would tear down the replacement instead of the attempt it ended. It is published last, since the abort cancels the very task that issued it.
- (rules) An intercepted turn excludes its partial output from the resumed request rather than removing it, so the interrupted text stays visible in the chat log where the user watched it appear. The resume reuses the stall-retry path for this reason, and dispatches through the turn queue as a user-originated send: the inference actor's abort arms a cancel tombstone that only a user-originated send lifts, so any other origin would drop the resumed turn silently and wedge the session.
- (rules) A stream rule that fails to compile, names no reachable stream, or carries an empty `body` is dropped with a warning rather than failing the turn. A rule fires at most three times per turn, which bounds a rule whose condition matches the guidance it injects without disarming a rule the model ignored once.
- (comments) A source comment asserts why the code is shaped as it is, not the process that produced it: no pointers to planning documents, no numbered acceptance criteria, no migration narrative. The standing exception is `default_jinn.toml`, whose `gap-check` attendant prompt tells the agent to search transcripts for the strings "acceptance criteria" and "AC1" — there those tokens are product behavior, and a sweep that removes them deletes a shipped feature. A sweep must exclude it by path, not by pattern.
- (sessions) Tool-call and tool-result index tracking lives on the session phase machine rather than on an individual phase, because a tool call's arguments stream in across the whole provider burst — which spans both busy phases — and the burst's first prose token drives the `Sending → Streaming` edge, so a per-phase copy is discarded by a transition that happens mid-arguments.
- (sessions) Tool-call tracking is cleared where the streaming turn ends rather than as a side effect of leaving a phase: a finished, errored, or cancelled stream, a stall-retry rewind, and the tool-use handoff that closes a burst whose calls have already been finalized.
- (sessions) Registering a tool call or tool result checks the session phase rather than the availability of a tracking map, because the maps are machine-level and always present. A result arriving with no turn in flight is refused before its entry is pushed, so a cancelled session accumulates no orphan entries.
